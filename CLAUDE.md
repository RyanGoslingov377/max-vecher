# max-vecher — контекст для Claude

Мини-приложение и бот для мессенджера МАКС (конкурс МАКС × Минобрнауки, трек «Досуг и развлечения»): подбираем вечер по настроению и зовём друзей карточкой «Иду / Может / Не могу» в групповом чате.

Продукт, план и задачи с номерами (Б4, Ф2…) — в документе команды: https://claude.ai/code/artifact/a21cfe51-a584-4ae4-8d55-b5dbe6b33651 (вкладка «План и задачи»). Номер задачи человек назовёт в начале сессии.

## С кем ты работаешь

- Два разработчика, у каждого свой Claude, общей памяти между вами нет. Бэкенд — новичок: объясняй простыми словами и давай команды по одной (cmd на Windows), если человек не просит иначе.
- По правилам хакатона ИИ — только помощник: команда должна понимать весь код и уметь объяснить его жюри. После каждого куска коротко объясняй, что написано и зачем, и предлагай человеку самому сделать небольшую правку.
- В начале сессии: `git checkout main`, `git pull`, `git log --oneline -10` — перескажи человеку, что влили с прошлого раза.

- Фронт держит все запросы к серверу в `web/api.js`. Пока адреса нет на сервере, там же заглушка в формате контракта ниже.

## Ветки и PR

Прямо в `main` не пушим. Одна задача = одна ветка = один PR.

1. Новая ветка от свежего `main`: `git checkout main` → `git pull` → `git checkout -b front/f2-screens` (префикс `back/` или `front/`, дальше номер и суть задачи).
2. Меняешь только файлы своей зоны, коммитишь маленькими кусками.
3. Перед PR: `python -m pytest` → `git pull origin main` (подтянуть свежий `main` в ветку) → `git push -u origin <ветка>`.
4. PR открывает человек по ссылке, которую печатает `git push`. Заголовок: «Ф2: экраны прототипа в web/». В описании три пункта: что сделано, как проверить, что не доделано. Описания PR — наш журнал работы.
5. На PR автоматически запускаются тесты и сборка Docker (`.github/workflows/checks.yml`). Мёрджим только с зелёными проверками: кнопка **Squash and merge**, потом **Delete branch**. Второй человек смотрит PR, если он на связи; если его нет дольше 2 часов, автор мёрджит сам.
6. После мёрджа: `git checkout main` → `git pull` → новая ветка под следующую задачу. В старую ветку больше не коммитим.
7. У каждого не больше одного открытого PR. На чужую невлитую ветку не опираемся — вместо неё заглушка.

## Безопасность

- Не используй `git push --force`, `git reset --hard`, `git clean`, `git checkout -- .`, `git rebase` и не удаляй файлы без явной просьбы человека. Ошибку исправляем новым коммитом или `git revert`.
- Перед коммитом проверь `git status`: в коммит не должны попасть `.env`, `.venv/`, `data/app.db`.
- `.env` не коммитить и не показывать. Токен бота не вставлять в код, логи и сообщения.
- Бот (long polling) работает только в одном месте — на хостинге Amvera. Локально у всех `BOT_ENABLED=0`: сервер и API работают без бота, токен не нужен. Два бота с одним токеном делят события случайным образом.
- Если бэкенду нужно проверить бота локально до сдачи: остановить приложение в Amvera → локально `BOT_ENABLED=1` → проверить → вернуть `BOT_ENABLED=0` → запустить приложение в Amvera. После сдачи 30.09 бота локально не запускаем вообще.
- Если `git pull` сообщает о конфликте, объясни человеку, что случилось, и разреши конфликт, сохранив изменения обоих.

## Стек и команды

- Python 3.12, FastAPI + uvicorn, httpx, SQLite (встроенный `sqlite3`), pytest. Фронт — ванильный HTML/CSS/JS без сборки и фреймворков.
- Первый запуск: `py -3.12 -m venv .venv` → `.venv\Scripts\activate` → `pip install -r requirements.txt` → `copy .env.example .env`.
- Запуск: `python -m uvicorn server.main:app --reload --port 3000`. Мини-приложение из `web/` — на http://localhost:3000, API — `/api/...`, документация API — `/docs`.
- Если порт 3000 занят, сервер уже запущен у человека и с `--reload` сам подхватывает правки в `.py`. Второй экземпляр не запускай.
- Тесты: `python -m pytest` — перед каждым PR и после каждой правки `data/events.json`.
- Docker (обязателен по правилам): `docker compose up --build`. В контейнере база лежит в `/data/app.db` (`DB_PATH` задан в `Dockerfile`), в compose это том `app-storage`.
- Хостинг — Amvera: собирает тот же `Dockerfile` по настройкам из `amvera.yml`, постоянный диск — `/data`, порт 3000. Токен и остальные переменные заданы в интерфейсе Amvera, не в репозитории. Адрес: https://max-vecher-gosuslugov233.amvera.io/ (он же отправлен организаторам как адрес мини-приложения). Amvera подключена к GitHub и сама забирает `main` после мёрджа; если новая версия не появилась — бэкенд жмёт пересборку в интерфейсе Amvera.

## Контракт API (фронт ↔ бэкенд)

Меняет только бэкенд, отдельным PR. Пока адреса нет, фронт держит заглушку в `web/api.js` в том же формате.

| Метод и адрес | Ответ | Статус |
| --- | --- | --- |
| `GET /api/pick?mood=&day=&budget=0\|1` | `{mood, day, budget, results: [{event, mood, score, over_budget}]}` | работает |
| `GET /api/me` | `{user, chat, start_param}` — кто и из какого чата открыл мини-приложение | работает |
| `POST /api/invites`, тело `{event_id}` | `{invite_id}`; бот шлёт карточку в чат, из которого открыто мини-приложение | Б5 |
| `GET /api/invites/{id}` | `{event, answers: [{name, answer}]}` | Б5 |
| `GET /api/stats` | `{going, went}` | Б7 |

- `mood`: charged, release, exhale, blue, learn, wild. `day`: today, tomorrow, saturday. `answer`: going, maybe, no.
- `event`: `id`, `title`, `place`, `starts_at` (ISO с `+03:00`) или `"anytime": true`, `price` (₽, 0 — бесплатно), `tags`, `nrg` и `dep` (0–2), `growth`, `why`, необязательный `ticket_url`.
- POST-запросы и `/api/me` идут с заголовком `X-Max-Init-Data: <window.WebApp.initData>`. Без заголовка или с неверной подписью — 401. При `DEV_AUTH=1` сервер без заголовка подставляет тестового пользователя `{id: 1, first_name: "Тест"}` и чат из `DEV_CHAT_ID` (только локально). Проверка — `server/auth.py`.
- id чата фронт не передаёт: сервер берёт его из подписанных данных МАКС.

## МАКС: что проверено

- Bot API: `https://platform-api.max.ru`, заголовок `Authorization: <токен>`. Документация: https://dev.max.ru/docs-api
- `platform-api2.max.ru` из примеров организаторов подписан сертификатом Минцифры (Russian Trusted CA), Python ему по умолчанию не доверяет. Адрес меняется через `MAX_API_URL` в `.env`; если перейдём на api2, в Docker-образ нужно добавить корневые сертификаты Минцифры.
- Кнопки `inline_keyboard`: callback, link, open_app, request_contact, request_geo_location, message. Нажатие приходит как update `message_callback`. Ответ `POST /answers?callback_id=…` с полем `message` заменяет исходное сообщение — так обновляется счётчик.
- Long polling: `GET /updates?timeout=30&marker=…`. В группе бот получает сообщения, только если он администратор.
- Мини-приложение: только https. Скрипт `<script src="https://st.max.ru/js/max-web-app.js"></script>`, объект `window.WebApp`: `initData`, `initDataUnsafe.user` / `.chat` / `.start_param`, `ready()`, `close()`, `openLink()`, `BackButton`. Документация: https://dev.max.ru/docs/webapps/bridge
- Проверка `initData`: секрет = HMAC-SHA256 с ключом `"WebAppData"` от токена; подпись = hex HMAC-SHA256 с этим секретом от пар `key=value` без `hash`, отсортированных по ключу и склеенных через `\n`. Перед реализацией сверить с примером: https://dev.max.ru/docs/webapps/validation
- Бота создали организаторы, адрес мини-приложения к нему привязывают они по ссылке из формы (задача О1).
